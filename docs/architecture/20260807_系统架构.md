- 一个 `TurnService`；
- 一个带 ApprovalRepository 的 `ToolExecutor`；

- 配置允许且已实现的 Tool；
- TUI `/tools` 使用的稳定 ToolDefinition 列表。

## Autopilot 权限与入口信任

Python Core 持有唯一 `PermissionState`，值为 `safe / smart / autopilot / yolo`。模式不是 Policy 的替代品：
WorkspaceGuard、敏感路径、exact argv、命令硬禁止、HTTPS/DNS/SSRF 和资源预算始终先执行，模式只决定通过硬校验后
是自动执行还是创建 Approval。

```mermaid
flowchart TD
    ENTRY["TUI / Feishu / Telegram / Discord"] --> VERIFY["Owner + private chat verification"]
    VERIFY -->|"本地或 Owner 私聊"| TRUSTED["trusted_owner = true"]
    VERIFY -->|"群聊或其他成员"| UNTRUSTED["trusted_owner = false"]
    UNTRUSTED --> DROP["移除 Personal extra read/write roots"]
    TRUSTED --> CTX["ToolContext"]
    DROP --> CTX
    MODE["PermissionState"] --> POLICY["PolicyEngine"]
    CTX --> POLICY
    POLICY --> HARD["Hard path / argv / network validation"]
    HARD -->|"deny"| DENY["Redacted Audit"]
    HARD -->|"approval"| WAIT["Bound Approval"]
    HARD -->|"allow"| EXEC["Tool execution"]
```

本地 Bridge 绑定 SQLite Owner。Channel 只有配置的 Owner 外部 ID 且 `chat_type=p2p` 时才传播 trusted 标记；
Owner 在群聊中也会降级。`/permissions` 在 TUI 通过 NDJSON `permissions.set` 切换，在 IM 中只由 Owner 私聊控制，
不会进入模型。活动 Turn 或 pending Approval 存在时切换失败关闭。

新 Personal 配置显式从 `autopilot` 启动；旧配置没有 `tools.mode` 时按 `safe` 加载。模式变化写入
`policy.mode_changed` 脱敏审计，只保存 old/new/source。完整状态表、操作和回滚见
[Autopilot 权限与紧凑审批 UI](../engineering/phase-2/autopilot-permissions-and-approval-ui.md)。

## 写入审批与续跑

```mermaid
sequenceDiagram
    autonumber
    actor User as 用户
    participant UI as TUI
    participant Exec as ToolExecutor
    participant Approval as ApprovalRepository
    participant Turn as TurnService
    participant Store as SQLite
    participant Model as Provider

    Exec->>Approval: create_waiting(normalized arguments)
    Approval->>Store: waiting ToolRun + pending Approval + Audit
    Exec-->>UI: approval_required
    UI->>UI: 缓存事件，不阻塞 Core
    Exec-->>Turn: approval ID
    Turn->>Store: parent Turn = waiting_approval
    Turn-->>UI: handle 返回
    UI->>UI: 打开 Modal，默认焦点 Deny
    alt Allow once / Session / Always
        User->>UI: Core 允许的 decision
        UI->>Turn: continue_approval(decision)
        Turn->>Approval: validate decision before side effect
        Turn->>Approval: approve + consume
        Turn->>Exec: execute_approved(bound ToolRun)
    else Deny 或 Esc
        User->>UI: Deny / Esc
        UI->>Turn: continue_approval(DENY)
        Turn->>Approval: deny
    end
    Turn->>Store: child Turn + Tool Message
    Turn->>Model: 基于真实结果继续
    Model-->>Turn: final answer
    Turn->>Store: child completed
    Turn-->>UI: turn_finished
```

Approval 绑定 Tool 名、canonical JSON 参数与 SHA-256；Owner、TTL、状态和单次 consume 都由 SQLite 条件更新
校验。TUI 不是安全边界，它只展示 Core 的 `grant_modes`。Session/Always 规则只在 Tool 成功后应用；Session
留在当前 PolicyEngine，Always 只保存 exact argv 或 exact hostname + port。文件写入与 inline AppleScript
不能持久授权。pi-tui ApprovalDialog 最大 84 列、18 行，固定标题、风险提示和决策区，只滚动参数详情；外层
Overlay 不再用裁剪隐藏底部按钮。

## Memory、Skills 与 Compaction

```mermaid
flowchart LR
    QUERY["当前 Query"] --> CONTEXT["ContextBuilder"]
    IDENTITY["SOUL.md + USER.md"] --> CONTEXT
    MEMORY["MEMORY.md + 今日/昨日 daily"] --> CONTEXT
    META["Skill metadata"] --> MATCH["确定性匹配，最多 3 个"]
    MATCH --> BODY["命中的 SKILL.md 正文"]
    BODY --> CONTEXT
    SUMMARY["最新 compaction summary"] --> CONTEXT
    RECENT["未覆盖的最近消息"] --> CONTEXT
    CONTEXT --> REQUEST["ModelRequest + runtime snapshot"]
```

- `MEMORY.md` 是 Owner 可审阅的长期真相源；`propose_memory` 经审批后只追加当日 daily memory。
- Memory 读取限制 64 KiB，拒绝符号链接、非法 UTF-8 和常见凭据模式。
- Skill 启动时只扫描 metadata；当前 Query 命中后才加载正文，最多 3 个，且不执行 Skill 代码。
- Memory、Skill 与 compaction 的版本/内容哈希进入 Turn runtime snapshot，便于回放。
- 估算上下文达到配置预算 80% 时，`ContextCompactor` 用当前 Provider 总结最旧连续 Turn，保留最近两轮和
  waiting approval；summary 写入现有 `messages` 表，原消息不删除。
- 摘要失败时不写半成品，当前请求退化为有界最近历史继续运行。

## RunEvent 投影

```mermaid
flowchart LR
    CORE["Turn / Runner / Executor"] --> EVENT["RunEvent"]
    EVENT -->|"model_text_delta"| ASSISTANT["one Markdown per Turn"]
    EVENT -->|"model_reasoning"| REASON["expandable provider reasoning"]
    EVENT -->|"model_usage"| METRICS["context / token / iteration / tool audit"]
    EVENT -->|"tool_*"| CARD["expandable ToolCard per call ID"]
    EVENT -->|"approval_required"| MODAL["Core-scoped Once / Session / Always / Deny"]
    EVENT -->|"turn_finished"| FINAL["persisted final content"]
```

事件只在对应数据库迁移完成后发送。普通 UI handler 异常被隔离且日志不含 payload；取消异常继续传播。模型
和 Tool 输出先移除 ANSI、C0/C1 控制字符，Tool 结果预览限制 2,000 字符，折叠详情
限制 8,000 字符，Markdown 不自动打开链接。`model_reasoning` 只投影 Provider 明确返回的
`reasoning_content`，不生成或猜测隐藏思维链。Token 缺失显示 `N/A`，不估算。

## 当前约束与下一阶段

- 单用户、一个 SQLite、一个活动 TUI Turn；默认终端链路是 Python launcher → Node UI → Python Core Bridge；

## Phase 5 当前多 Channel 架构

```mermaid
flowchart TB
    U["Owner"] --> F["Feishu WebSocket"]
    U --> T["Telegram long polling"]
    U --> D["Discord Gateway"]

    F --> FP["Feishu Transport → Delivery → Manager"]
    T --> TP["Telegram Transport → Delivery → Manager"]
    D --> DP["Discord Transport → Delivery → Manager"]

    FP --> R["one AgentRuntime"]
    TP --> R
    DP --> R
    R --> P["Provider + Policy + 10 Tools"]
    R <--> DB["SQLite Inbox / Outbox / Session / Approval"]
    R <--> M["Markdown Memory + Skills"]
```

静态 preflight 是 all-or-none：任一 enabled Channel 缺 SDK、Token 或 Owner relationship 时，在创建 Provider、SDK
Client 和网络连接前失败。运行期则局部隔离：每个平台有独立 Transport、DeliveryWorker、ChannelManager、queue 和
Experience activity；断线只把当前 pipeline 标为 degraded。关停先关闭全部 admission，再以反向平台/反向组件顺序
清理，最后只关闭一次共享 AgentRuntime。

Approval durable payload 使用平台中立 v2 envelope；飞书旧 v1 Card 只读兼容。Telegram/Discord 当前用纯文本
fallback，所有决定仍由 Core SQLite 条件更新校验 Owner、TTL、scope 和单次 consume。

Feishu Live Runner 位于生产链旁边，不在生产链内部复制 Agent：

```mermaid
flowchart LR
    LR["Feishu Live Runner"] --> GP["GatewayProcess"]
    GP --> PG["production miniclaw gateway"]
    PG --> FP["Feishu pipeline"]
    FP --> AR["shared AgentRuntime"]
    AR <--> DB["SQLite durable truth"]
    LR -. "read-only checkpoint/evidence" .-> DB
    LR --> ER["0600 redacted Evidence"]
```

Runner 在 `--confirm-live` 前不读 config/state/secret，也不联网；确认后要求只有 Feishu enabled、clean commit、
Doctor 无 FAIL、0 旧 pending Approval。自动 evidence 失败时人工不能覆盖。它最多发送两次 SIGTERM，不发送
SIGKILL，不写假业务事实。
