# 未解析的工具调用标记泄漏为正文

> 日期：2026-08-11
> 文档类型：事故根因分析与修复记录
> 状态：`IMPLEMENTED`（2026-08-11）

## 1. 现象

用户提问「我最长的 3 个飞书文档是哪 3 个」，回合跑满 32 轮上限后结束，最终回复是一串乱码：

```
<｜｜DSML｜｜tool_calls>
<｜｜DSML｜｜invoke name="run_command">
<｜｜DSML｜｜parameter name="args" string="false">["/Users/nedonion/.lobster0/workspace/fetch_docs.py","31"]</｜｜DSML｜｜parameter>
<｜｜DSML｜｜parameter name="program" string="true">python3</｜｜DSML｜｜parameter>
...
```

代价：4 分 38 秒、**约 100 万 token**、36 次工具调用、32 轮迭代，最终没有回答问题。

## 2. 根因

那些竖线是 **U+FF5C 全角竖线**（`｜`，非 ASCII `|`），这是 DeepSeek 内部工具调用标记语法的一部分。
正常情况下模型应当把工具调用编码进 OpenAI 兼容的结构化 `tool_calls` 字段；这次它把**原始标记文本**
直接写进了 `content`。

排除的可能性（逐条实测，不是推测）：

| 假设 | 验证方式 | 结论 |
| --- | --- | --- |
| 模型不支持 function calling | 直接对 `api.deepseek.com` 发一次带 `tools` 的真实请求 | **排除**：正常返回 `finish_reason: tool_calls` 与结构化 `tool_calls`，`content` 为空 |
| 请求里没传 `tools` 参数 | 查 `providers/openai_compatible.py:157` | **排除**：`request.tools` 非空时正常写入 payload |
| Provider 解析逻辑有误 | 查 `_merge_tool_fragments` / `_finish_tools` | **排除**：走标准 `tool_calls` 字段解析，代码里根本没有 "DSML" 字样 |

所以这是**模型侧的退化行为**：在极长上下文（本次约 100 万 token 累计）下，模型没有走结构化输出通道。
我们无法修复模型本身。

## 3. 修复：把它识别为失败，而不是当正常回复

修复前的行为是最糟的组合——既没有执行任何工具，又把这坨标记当作最终答案保存并展示给用户，同时白白
消耗了整轮预算。

`agent/runner.py` 新增 `looks_like_unparsed_tool_call()`：在模型返回「无工具调用 + 有正文」这条既有
分支上，额外判断正文是否是未解析的工具调用标记，是则抛出新的 `UnparsedToolCallError`。

匹配规则刻意收窄为「尖括号 + 竖线（全角或半角）+ `tool_calls`/`invoke`」：

```python
r"<\s*/?\s*[|｜]{1,2}\s*(?:DSML\s*[|｜]{1,2}\s*)?(?:tool_calls|invoke)\b"
```

有测试锁定**不能误伤**正常回答：提到工具名（"我用 run_command 跑了一下"）、贴出代码块、甚至正文里
出现 `<invoke>` 这个 XML 标签，都不会命中——只有模型专用的竖线标记才会。

`agent/turn.py` 的错误码映射表新增 `(UnparsedToolCallError, "unparsed_tool_call")`，让这次失败在
Turn 记录、Channel 展示与 Desktop 时间线上都有稳定、可辨识的错误码，而不是伪装成一次成功。

## 4. 轮次上限的调整

用户要求「去掉上限，加一个停止按钮就行」。停止按钮**本来就有**（`task-workbench.tsx`，运行中显示），
只是此前样式是次要按钮、与「发送」挤在一起，用户没找到；已在同一批改动中提为红色主按钮。

上限则**不建议去掉**：本次事故正是"转 32 轮什么也没做成"，去掉上限只会变成转更多轮、烧更多钱，
上限恰恰限制了损失。折中把 `~/.lobster0/config.toml` 调为：

```toml
max_tool_iterations = 120       # 原 32
max_tool_iterations_hard = 200  # 原 64
```

软上限不得超过硬上限，两个都要改；改后 `lobster0 doctor` 的 `config` 检查仍为 PASS。原配置已备份为
`config.toml.bak-<timestamp>`。这是纯配置项，不需要改代码，用户随时可自行调整。

## 5. 验证

- `tests/test_agent_runner.py` 新增 `UnparsedToolCallTextTest`（3 条）：真实事故文本（全角竖线）、
  半角变体、以及 5 种不应误判的正常文本；
- 相关模块全绿：`test_agent_runner` 30/30、`test_bridge_server` 12/12、`test_channel_manager` 23/23，
  `ruff check` 通过；
- 全量 1565 条里有 82 error + 1 failure，**全部集中在 `test_install_runtime` / `test_install_bootstrap`**。
  用 `git stash` 撤掉本次改动后重跑，同样的 82 个 error 依旧存在，确认是环境缺失导致的既有问题
  （本地缺 `python3.12` fixture），与本次修改无关。

## 6. 遗留

- 本次只做了**检测与快速失败**。更进一步的做法是在检测到标记后尝试解析出真实的工具调用并继续执行，
  但那等于在应用层实现一套模型私有格式的解析器，会与 Provider 的标准通道产生两套真相，风险大于收益，
  暂不做；
- 触发这次退化的直接诱因是上下文过长。真正的治本方向是上下文预算与压缩策略，属于既有的 compaction
  范畴，不在本次范围内。
