# Web 控制台（`lobster0 web`）

> 状态：`CODE COMPLETE / JS 门禁在本机未执行 / 仅回环默认`

本文记录把 Electron Renderer 原封不动搬到浏览器里的完整事实：换掉了什么、**没有**换掉什么、
到底谁能访问到它、以及哪些结论是跑出来的、哪些只是写出来的。

目标读者是要 review 这次改动或要真的把它跑起来的人。它不是产品说明，
所以对「保护了什么、没保护什么」一律按最坏情况写。

---

## 1. 为什么这件事是小改动

Renderer 只通过**一个**对象接触 Electron：`window.lobster0`。而这个对象的构造函数
`createDesktopApi(invoke, subscribe)`（`desktop/src/common/api.ts`）**本来就与传输无关**——
它只要一个「发请求」函数和一个「订阅推送」函数。Preload 传进去的是 Electron IPC：

```ts
createDesktopApi(
  (channel, payload) => ipcRenderer.invoke(channel, payload),
  (channel, handler) => { /* ipcRenderer.on */ },
);
```

主进程一侧的 `registerDesktopIpc(register, bridge, publishFrame, ...)`（`desktop/src/main/ipc.ts`）
对称地也与传输无关：它只要一个「注册 handler」函数和一个「广播事件」函数。

所以 Web 控制台**不是**一个新前端，而是同一份契约的第二种传输：

| 层 | Electron | Web |
| --- | --- | --- |
| Renderer 组件 | `desktop/src/renderer/*` | **完全相同，零改动** |
| `window.lobster0` | `desktop/src/preload/index.ts`（contextBridge） | `desktop/src/web/client.ts`（fetch + EventSource） |
| 传输 | Electron IPC | HTTP POST + SSE |
| Handler 注册 | `ipcMain.handle` | `desktop/src/web/server.ts` 的 channel 表 |
| 事件广播 | `webContents.send` | SSE 广播 |
| Bridge 生命周期 | `desktop/src/main/index.ts` | `desktop/src/web/server-main.ts` |
| Bridge 客户端 | `BridgeService` + `BridgeClient` | **完全相同，零改动** |

`bridge-service.ts`、`ipc.ts`、`common/api.ts`、整个 `renderer/` 都是原样复用。
这也是选 Node 而不是 Python 写这个 server 的唯一理由：Bridge 的 stdio 客户端、
turn/approval 状态机和 20 多个请求的字段级校验全都已经在 TypeScript 里了，
用 Python 重写等于把约 1500 行必须逐字保持同步的逻辑复制一份。

## 2. 传输选型：HTTP POST + SSE，不是 WebSocket

契约的形状是「多次请求/响应 + 一条单向服务端推送」。WebSocket 的双向能力在这里没有用武之地。
选 SSE 的四条具体理由：

1. **形状匹配**：`onFrame` 是纯单向 server→client。SSE 就是这个东西，WebSocket 是它的超集。
2. **零新依赖**：`node:http` 直接就能写 SSE。WebSocket 要么引入 `ws`，要么手写 RFC 6455 帧协议。
   本仓库对新依赖一贯保守。
3. **穿隧道**：SSE 是一条普通的 HTTP 长响应，没有 `Upgrade` 握手。SSH 端口转发、
   以及任何中间的 HTTP 代理都不需要额外配置。WebSocket 的 `Upgrade` 经常是代理配置里第一个踩的坑。
4. **鉴权不需要把密钥放进 URL**：浏览器的 `WebSocket()` 和 `EventSource` 都**不能**设置自定义请求头。
   WebSocket 因此几乎总是被逼把 token 塞进 query string——而本仓库明确禁止密钥出现在 URL 里。
   SSE 走 Cookie，天然避开这一点（见 §4）。

代价：SSE 只能传文本、单向，且浏览器对同一 origin 的并发连接有上限。三条对本场景都不构成问题——
控制台只开一条 SSE 连接，帧本来就是 JSON 文本，而反向通道用的是普通 POST。

### 帧的顺序

SSE 在单条连接上严格保序，这是协议保证。server 侧的广播是同步 `write`，
`BridgeService.handleFrame` 也是同步遍历 handler，所以从 Bridge stdout 到浏览器 `onmessage`
全链路没有任何重排点。`desktop/test/web-server.test.ts` 对此有一条断言：连续推入
`turn_started → agent_delta ×N → turn_finished`，浏览器侧收到的顺序必须逐字一致。

**没有做**断线重放。SSE 的 `Last-Event-ID` 重连机制没有启用，因为 Bridge 侧不存在帧的持久缓冲——
断线期间发生的 delta 就是丢了。重连后 Renderer 会看到一个不完整的 timeline。
这是已知缺口，不是已解决的问题。

## 3. 审批提示怎么到浏览器

和 Electron 完全同一条路，只是最后一跳换了：

```
Python Bridge (stdout NDJSON)
  → BridgeClient.consume            （tui/src/bridge-client.ts，未改动）
  → BridgeService.handleFrame       （置 waiting_approval，未改动）
  → publishFrame                    （Web 的实现：写 SSE）
  → EventSource.onmessage           （desktop/src/web/client.ts）
  → createDesktopApi 的 subscribe
  → TaskWorkbench 的 window.lobster0.onFrame（未改动）
  → reduceDesktopFrame → pendingApproval → 渲染审批卡片
```

用户点「允许/拒绝」时，`resolveApproval(approvalId, decision)` 走的是普通 POST，
落到与 Electron 相同的 `validateApprovalInput` 校验和相同的 `BridgeService.resolveApproval`。

## 4. 安全姿态——按最坏情况写

这个 Agent 能执行命令、读写文件、驱动浏览器。所以这一节按「谁能拿到它」而不是
「我们打算给谁」来写。

### 4.1 默认：只绑回环，没有鉴权

默认监听 `127.0.0.1`。**默认情况下没有任何 token、没有任何登录**。
唯一的保护是操作系统的 socket 绑定：非本机的数据包到不了回环地址。

明确说清楚这意味着什么：

- 同一台机器上的**任何**本地用户、任何本地进程，都能完整访问这个控制台。回环不区分用户。
- 因此这个默认值只在「机器是你自己的、且你信任机器上所有本地用户」时才成立。
- 多用户共享主机上不要用默认配置。

### 4.2 远程访问的既定路径：SSH 端口转发

不要给它开公网。既定用法是把回环端口转发到你的设备上：

```sh
ssh -N -L 4180:127.0.0.1:4180 you@your-host
```

然后在手机/iPad/另一台笔记本上访问 `http://127.0.0.1:4180`。
鉴权、加密、可审计性全部由 SSH 承担，控制台本身仍然只绑回环。
**这是推荐路径**，因为它把认证交给了一个远比本文这几百行代码更值得信任的东西。

### 4.3 非回环绑定：必须显式开 + 必须有 token，否则拒绝启动

`--host` 指定任何非回环地址时，`resolveBindOptions` 会：

- 要求环境变量 `LOBSTER0_WEB_TOKEN` 存在且长度 ≥ 32；**缺失就拒绝启动**，不降级、不回退回环、
  不自动生成。启动失败比静默地少一层保护好。
- token 只从环境变量读，**不接受命令行参数**——参数会出现在 `ps` 输出里，对同机其他用户可见。
- 向 stderr 打印一条醒目警告，说明这台 Agent 现在对网络可达。
- token 值本身不进任何日志。server 的日志里只出现 `token=<redacted>`。

浏览器怎么带上 token：登录页把 token 放在 **POST 请求体**里发给 `/api/session`，
server 用 `timingSafeEqual` 比对，通过后下发一个 `HttpOnly; SameSite=Strict; Path=/` 的
Cookie，值是**本进程随机生成的 session id**，不是 token 本身。所以：

- token 不出现在 URL、不出现在 query string、不存进浏览器。
- session id 只存在内存里，server 一退出就全部失效。
- Cookie 是 `HttpOnly`，页面 JS 读不到。

### 4.4 CSRF 与 DNS rebinding——这一节请重点 review

「本地 HTTP server + Cookie」这个组合的经典攻击面是：你在浏览器里打开的**任意**恶意网页，
都可以向 `http://127.0.0.1:4180` 发请求，而浏览器会自动带上 Cookie。
DNS rebinding 还能让攻击者把自己的域名解析到 `127.0.0.1`，从而绕过 origin 检查。

三道独立的防线：

1. **不输出任何 CORS 头**。server 永远不发 `Access-Control-Allow-Origin` 等头。
2. **所有 API 请求必须带自定义头 `X-Lobster0-Console: 1`**。跨域 `fetch` 带自定义头会先触发
   CORS 预检，而预检因为第 1 条必然失败。这挡住了跨源 JS 发起的调用。
3. **`Host` 头白名单**。绑回环时只接受 `Host` 为 `127.0.0.1:<port>`、`[::1]:<port>` 或
   `localhost:<port>`。DNS rebinding 打过来的请求 `Host` 是攻击者的域名，在这里被拒。
   这是专门针对 rebinding 的那道防线，因为 rebinding 恰恰能骗过 origin 检查。

另外 `Origin` 头存在且不等于本 server 的 origin 时，直接拒绝。

### 4.5 明确**没有**保护的东西

- **没有 TLS。** 流量是明文 HTTP。这是回环 + SSH 隧道模型的直接结果——加密由 SSH 提供。
  如果你无视 §4.2 把它绑到公网，那你的 token 和全部对话内容都在明文里裸奔。
- **没有限流、没有审计日志、没有多用户、没有权限分级。** 单 owner 模型，与产品其余部分一致。
- **没有防本地提权。** 见 §4.1。
- **没有 CSP 之外的沙箱。** 浏览器页面本身是可信的（我们自己构建的）。

## 5. Web 侧刻意不支持的两个能力

`chooseWorkspace()` 和 `pickAttachment()` 在 Electron 里打开的是**原生文件对话框**，
返回一个宿主机上的绝对路径。浏览器里没有等价物。

Web server 对这两个 channel 一律返回 `null`，也就是契约里「用户取消了」的语义。
Renderer 对 `null` 早就有正确处理（直接 return，不报错），所以**不需要改任何组件**。

这里刻意**没有**选择另一条路：让浏览器把任意路径字符串传给 `stageAttachment`。
那会把一个「读取宿主机任意文件」的原语交给浏览器侧，是明确的安全退步。
真要在 Web 上支持附件，正确做法是新增一个上传端点、由 server 把字节落到 ArtifactStore，
这需要扩展 `DesktopApi` 契约，属于后续工作，不在本次范围内。

**后果要说清楚**：Web 控制台目前**不能**添加附件，也**不能**切换工作目录。点击对应入口不会有反应。

## 6. 启动方式

沿用 `lobster0` 既有的 launcher 约定（与 `tui_launcher.py` 同构）：

```sh
lobster0 web                      # 127.0.0.1:4180
lobster0 web --port 8080
lobster0 web --host 0.0.0.0       # 没有 LOBSTER0_WEB_TOKEN 会直接拒绝启动
```

`src/lobster0/web_launcher.py` 负责：校验 Node 版本落在已验证的 LTS 区间
（22.22.3～<23 或 24.15.0～<25）、确认 `desktop/out/web/server/index.js` 已构建、
清洗掉 `NODE_OPTIONS`/`NODE_PATH` 这类注入变量后再 `spawn`，全程 `shell=False` + 精确 argv。
与 `tui_launcher` 的唯一区别是它**不做 fallback**——Web 控制台没有降级形态，
条件不满足就报错退出。

构建（`build:web` 依赖 `tui/dist`，因为 server 会把 `BridgeClient` 打进产物）：

```sh
pnpm --dir tui install && pnpm --dir tui build
pnpm --dir desktop install
pnpm --dir desktop run build:web
```

产物落在 `desktop/out/web/client/`（浏览器）与 `desktop/out/web/server/index.js`（Node）。

## 8. review 时最该盯的地方

按风险从高到低：

1. **§4.4 的三道防线是否真的都在生效**，尤其是 `Host` 白名单——它是唯一挡 DNS rebinding 的东西。
   如果 `Host` 校验有一个绕过，回环默认配置就等于对任何能诱导 owner 打开一个网页的人开放。
2. **`resolveBindOptions` 有没有任何路径能在无 token 的情况下绑上非回环地址。**
   包括 `--host` 传入 `0.0.0.0`、`::`、`0`、十进制整型 IP（如 `2130706433`）、
   以及各种 `127.x` 之外但实际可达的写法。
3. **静态文件服务的路径穿越**：`out/web/client/` 之外的任何文件都不该被读到。
4. **`bridge.stop()` 是不是在所有退出路径上都被调用**——否则 Python 子进程会泄漏。
5. §7 的诚实性：不要在别处把未执行的门禁写成已通过。
