# Desktop 空态与侧边栏可用性修复

> 日期：2026-08-11
> 文档类型：D1 跟进修复实现记录
> 状态：`IMPLEMENTED`（2026-08-11）
> 上位设计：[D1 打开即聊设计](../../superpowers/specs/2026-08-10-desktop-d1-conversation-shell-design.md)
> 视觉基准：[Claude 风格视觉迁移](../../superpowers/specs/2026-08-11-desktop-visual-refresh-claude-inspired-design.md)

## 1. 触发来源

用户在真实使用中反馈三点（原话）：

1. "这个新建对话窗口太诡异了"；
2. "为什么 Logo 还是 M 都不需要有 Logo 在这里吧"；
3. "左侧侧边栏的样式能给我整体优化一下吗"。

## 2. 问题 1：空态出现两层重复标题

### 根因

[task-workbench.tsx](../../../desktop/src/renderer/task-workbench.tsx) 无论有没有对话，都会渲染
`conversation-header`（`CONVERSATION` + `新对话` + `等待开始` 状态标签）。空态下它与居中的
`conversation-invite`（`今天想完成什么？`）语义重复，中间还被撑出一大片空白，视觉上像是页面加载了一半。

对照 ClawX 和 Claude 的空态：都是**只有一个居中的大标题 + 输入框**，没有额外顶栏。

### 方案

空态不渲染 `conversation-header`，整块区域交给 `conversation-invite`；`.conversation-panel[data-mode="empty"]`
的 grid 行数从 `auto minmax(0,1fr)` 改为单行 `minmax(0,1fr)`。有对话时行为完全不变（顶栏照常显示当前
状态），因此不影响运行中/审批/失败态的可见性。

顺带把顶栏标题里的三元表达式去掉——它只在 `emptyTask === false` 时渲染，`新对话` 分支已成死代码。

## 3. 问题 2：Logo 仍是重命名前的 "M"

`brand-mark` 是硬编码字符串 `"M"`（MiniClaw 的首字母），重命名为 Lobster0 后未同步。用户明确表示
这个位置不需要 Logo，因此整块移除，侧栏顶部只保留 `Lobster0` 文字，`.brand-mark` 的 CSS 一并删除
（否则是死规则）。`.brand` 改为固定行高，与下方「新建对话」按钮和导航项的高度节奏对齐（第三轮把这套
节奏统一提到 36px，见 §4.2）。

## 4. 问题 3：侧边栏优化

| 项 | 问题 | 处理 |
| --- | --- | --- |
| 历史会话状态 | 直接渲染 Core 的原始枚举串（`waiting_approval` / `completed` / `failed`），既是英文技术术语，又因为每条都显示而变成噪音 | 新增 `sessionStatusLabel()`：`completed` 映射为 `null` 不渲染（它是绝大多数会话的常态），其余翻译成中文并渲染为小胶囊；`failed` 红、`waiting_approval` 橙、`running`/`queued` 用强调色，与语义色保持一致 |
| 未知状态 | —— | 原样透出而不是静默吞掉，便于发现 Core 新增状态；有测试锁定该行为 |
| 底部 `W1` 徽标 | 内部阶段代号，对用户无意义 | 移除，`.sidebar-status` 从三列 grid 简化为 flex |
| 底部文案 | `Core ready` / `Core offline` 是英文 | 改为「已连接本地 Core」/「未连接本地 Core」 |
| 自动化页说明 | 文案里残留 "W1 仅提供只读信息" | 改为「当前为只读」 |

### 4.1 历史对话按时间分组（第二轮）

用户确认第一轮效果后要求继续，补上 ClawX 那样的时间分组。新增
[session-groups.ts](../../../desktop/src/renderer/session-groups.ts)：

- `sessionGroupKey(updatedAt, now)` 把会话分到 `today` / `yesterday` / `week`（7 天内）/
  `month`（30 天内）/ `earlier` / `unknown` 六档；
- `groupSessionsByRecency()` 保留 Core 已有的 `updated_at DESC` 组内顺序，丢弃空分组；
- `SESSION_GROUP_LABELS` 提供中文标题（今天 / 昨天 / 最近 7 天 / 最近 30 天 / 更早 / 时间未知）。

**关键正确性点：按本地日历日分组，而不是按经过的小时数。** Core 返回的是 UTC ISO 时间戳
（如 `2026-08-10T20:55:22+00:00`），而用户感知的"今天/昨天"是本地日历日。若用毫秒差除以 24h，
东八区凌晨的会话会被误判成"昨天"——因为它距当前不足 24 小时却已跨过本地零点。实现把两个时间点
都归一化到各自本地日的 `00:00` 再算天数差，测试里专门有一条用例锁定这个边界（今天 00:30 与昨天
23:30 相距不到 24 小时，但必须落进不同分组）。

另外两个兜底：无法解析的时间戳归入 `unknown` 而不是抛错或静默丢弃；时钟回拨/Core 时间超前导致的
未来时间戳按 `today` 处理，不会掉进 `earlier`。

渲染上，`.sidebar-recent-group` 之间用 10px 外边距拉开，比组内条目 1px 的间距明显，让分段一眼可辨；
原先固定的"最近对话"单一标题由各分组标题取代。

### 4.2 去掉大面积色块（第三轮）

用户看到实际效果后指出「新建按钮太矮太窄」「不要搞这么大块的颜色 去掉」，并要求对齐 Claude /
ClawX 的极简做法——查证两者的侧栏：New Chat 都是纯文字 + 图标、**没有实心背景**，选中态只用中性
浅灰。据此：

- `.sidebar-create` 去掉棕色实心填充，靠位置与字重区分主次；
- `.nav-item[data-active]` 从 `primary-muted`（浅棕）改为中性 `surface-raised`；
- 强调色不再用于任何大面积填充，只保留在状态胶囊这类功能性小标记上；
- 尺寸放松：条目 32→36px、圆角 6→8px、字号 13→14px，品牌区 32→36px 并加大与下方间距。

## 5. 时间线聚合为「过程」块

用户反馈：「工具的调用放到思考里面，思考我希望是一整段的可以收起的状态」「工具的执行为什么显示了
两段」，并进一步明确「我希望那一大块是【过程】里面包含了工具调用和思考」。

### 5.1 工具重复两行的根因

不是布局问题，是数据本身重复：[agent/runner.py:486](../../../src/lobster0/agent/runner.py) 发出
`event.tool_requested` 时 `"summary": call.name`——**摘要就等于工具名**。渲染层同时输出
`<span>{item.name}</span>` 和 `<Markdown content={item.summary} />`，于是同一个 `run_command`
被打印两遍。

修在展示层：新增 `toolDetail()`，只有摘要 trim 后非空**且不等于工具名**时才额外渲染一行。不改 Core
的 `summary` 语义——它同时被审批卡片等其他消费方使用，改动影响面超出本次范围；根因记录在此，留待
后续单独处理（让 Core 复用 `_approval_summary` 那种带参数信息的摘要会更有价值）。

### 5.2 聚合

新增 [timeline-blocks.ts](../../../desktop/src/renderer/timeline-blocks.ts) 的 `groupTimeline()`：把
时间线压成「消息」与「过程」两种块，连续的思考 / 工具调用 / 本地提示合并进同一个「过程」块，遇到
用户或助手发言即结束当前块——保证过程始终归属它所在的那一段对话。折叠时只显示一行 `过程 · N 步`，
展开后用一条细竖线把整段过程收拢成一块。

折叠状态改为**块级本地 state**：过程块是纯展示层聚合出来的概念，pi-tui 状态库里没有对应实体，
因此不再复用它逐条 item 的 `expanded` 字段。随之删除已成死代码的 `toggleDesktopItem()` 与
`collapseNewReasoning()`（后者原本用于覆盖新 reasoning 的默认展开值，块级折叠接管后不再需要）。

## 6. 一处自我纠正

截图上邀请区看起来左右不对称、偏左，一度准备调整 `.conversation-invite` 的居中方式。改之前先用
`getBoundingClientRect()` 实测，结果是 `leftGap = rightGap = 193px`，**本来就是精确居中的**——视觉
偏移感来自输入框内左对齐的 placeholder 和右下角发送按钮的重量分布。因此未做任何改动，避免了去"修"
一段正确的代码。

## 9. 第四轮：统一按钮、运行指标、助手回复去气泡

用户在真实使用中继续反馈四点，逐条处理如下。

### 9.1 「新建对话」与导航项不一致

用户先说「宽度不一致」，随后更正为「应该是高度」，最后给出结论性要求：「你就照着【对话】的样式来啊，
只不过改个最开始的 Icon 改成 + 加号即可」。

先用 `getBoundingClientRect()` 实测：四个按钮**宽高完全一致**（219 × 36px，left 均为 10px）。真正的
差异是**字重与颜色**——`.sidebar-create` 额外覆盖了 `color: foreground` 与 `font-weight: medium`，
而导航项是次级灰 + 常规字重，于是看起来是两种控件。按用户要求删掉这两行覆盖，只保留开头的 `+`
图标做区分；同时把全角 `＋` 换成半角 `+`，与其他导航图标的视觉重量对齐。

间距节奏一并统一：`.sidebar` 的 gap 由 8px 收到 2px，与 `.navigation` 内部一致，避免「新建对话」
因为间隔更大而显得孤立；历史区改用自身 `margin-top` 撑开呼吸，而不是放大 `.sidebar` 的 gap
（后者会连带拉开导航项之间的距离）。

### 9.2 运行指标缺失

第一轮删掉右侧结果面板时，`telemetry`（耗时 / token / 工具次数 / 迭代轮次）随之消失。用户要求
「我希望看到执行时候的用时 token 量 工具次数等等」。新增
[telemetry-facts.ts](../../../desktop/src/renderer/telemetry-facts.ts)，把 `AppState.telemetry`
整理成顶栏右侧的紧凑事实列表：

- **只输出已真实测到的项**：未跑过的回合不显示任何数字，避免 0 看起来像"跑完了但什么都没做"；
- 耗时按量级切换格式：`0.4s` / `12.9s` / `3m15s`，短耗时保留一位小数而不是四舍五入成 `0s`；
- Token 优先用本回合 `inputTokens + outputTokens` 的精确用量，只有 Provider 未给出分项时才退回
  `contextTokens` 估算值；
- 固定顺序为 耗时 → Token → 工具调用 → 模型轮次，并用等宽字体、低对比呈现，不与状态标签争夺注意力。

### 9.3 助手回复去气泡

用户要求「龙虾的回复就不用加气泡了 自然融入背景色为一体即可」。`.message-assistant` 去掉圆角、
内边距与背景填充，宽度放宽到 100%（助手回复是阅读主体，不该被限制在 78%）；用户消息保留气泡，
作为来源区分。

### 9.4 工具摘要在 Core 侧修正

§5.1 记录的根因（`summary === tool_name`）在本轮从源头修掉：把 `tools/executor.py` 里的私有
`_approval_summary()` 提升为 `agent/events.py` 的公开 `tool_display_summary()`，`runner.py` 发
`event.tool_requested` 时改用它。

选这个位置是因为依赖方向已经成立且无新增：`tools/executor.py` 本来就 import `agent/events`，而
`agent/events.py` 只依赖 `providers/base`，不会成环。审批卡片与 Tool 事件从此共用同一份摘要，
保证「批准前看到的描述」与「执行时看到的描述」完全一致。

摘要的脱敏语义原样保留并补齐测试：`run_command` 只暴露程序名与参数个数（不含完整 argv）、
`http_get` 只保留 authority（丢弃可能含 token 的 path/query）、`browser_type` 只报字符数（不含
键入内容）、带 path 的只保留 basename（不泄露目录结构）。另有一条测试锁定「摘要永远不等于裸工具名」，
从源头防止前端退化成重复两行。

Desktop 侧的 `toolDetail()` 去重保留——它是对任意 Core 版本的防御，即使将来又有工具把摘要设成工具名，
界面也不会重复渲染。

### 9.5 验证

- Desktop：66/66 通过（57 + telemetry 的 9 条），typecheck / build 干净；
- Python：`tests.test_run_events`（新增 7 条摘要用例）、`tests.test_tool_executor`、
  `tests.test_agent_runner` 合计 70/70 通过，`ruff` 干净；
- 全量 Python 套件 1555 条中有 83 条 error，**全部集中在 `test_install_runtime`(82) 与
  `test_release_bundles`(1)**，原因是本机缺少 `python3.12` fixture
  （`FileNotFoundError: .../bin/python3.12`）。已用 `git stash` 把本轮改动移除后重跑同一条用例，
  确认在原始代码上同样失败——属于既有环境问题，与本次改动无关；
- 视觉：用真实 `App` + 真实 `ServerFrame` 序列核对，确认顶栏显示
  `12.9s / 8.3k token / 1 次工具 / 2 轮`、助手回复无气泡、侧栏两类按钮同款。

> 教训记录：本轮一度用 `python -m unittest ... | tail -12` 判断全量结果，看到 exit code 0 就认为
> 通过——那其实是 `tail` 的退出码，掩盖了 unittest 的失败。判断测试结果必须取被测命令自身的退出码，
> 不能让它出现在管道左侧。
