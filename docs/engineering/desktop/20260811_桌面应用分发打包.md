# 桌面应用分发打包（electron-builder）

> 状态：`PACKAGING CONFIG VERIFIED / LINUX BUILD UNVERIFIED / UNSIGNED`

本文记录 `desktop/` 从「只能在 checkout 里 build」升级为「产出可下载安装包」的完整事实：
用什么打包、产出哪些文件、版本怎么绑、发布链路怎么接、以及**签名到底有没有做**。

---

## 1. 打包工具与固定版本

| 事实 | 取值 |
| --- | --- |
| 打包工具 | `electron-builder` |
| 固定版本 | `26.15.3`（devDependency，精确版本，无 `^`/`~`） |
| 配置文件 | `desktop/electron-builder.json` |
| 触发方式 | `pnpm --dir desktop exec electron-builder --config electron-builder.json --publish never --mac\|--linux` |

选 `electron-builder` 的理由：它是 Electron 生态里唯一同时覆盖 dmg/zip/AppImage 且不需要
额外原生工具链的成熟方案，且配置是纯声明式 JSON——这正好能被本仓库的离线配置契约测试断言。

选 `26.15.3` 而不是更新的 `26.15.7`：`26.15.3` 是 npm `latest` dist-tag 所指的版本，也就是上游
当前默认推荐给所有使用者的构建；`26.15.4`～`26.15.7` 只挂在 `v26` tag 下，不是上游的默认建议。
本仓库对所有外部组件一律取「上游默认推荐 + 精确固定」，这里保持一致。

### 打包工具链的诚实边界

`electron-builder` 在构建期会自己去 GitHub 拉取 Electron 43.2.0 的官方二进制、`dmgbuild`
bundle 与 AppImage runtime。这些下载**不在** `release/runtime-versions.json` 的固定 URL +
SHA-256 体系里，由 electron-builder 自己校验。这是本次变更相对「所有外部输入都由仓库固定
哈希」这一姿态的唯一让步，收敛它需要另做一个 electron 二进制预取步骤，属于后续工作。

## 2. 产出的平台与格式

| 平台 | 格式 | 架构 | 产物名 |
| --- | --- | --- | --- |
| macOS | `.dmg` | arm64 / x64 | `lobster0-desktop-<version>-macos-<arch>.dmg` |
| macOS | `.zip` | arm64 / x64 | `lobster0-desktop-<version>-macos-<arch>.zip` |
| Linux | `.AppImage` | x64 / arm64 | `lobster0-desktop-<version>-linux-<arch>.AppImage` |

一次 Release 共 6 个桌面产物（4 个 macOS + 2 个 Linux），每个都带一份 `.sha256` sidecar。

### 为什么 Linux 只有 AppImage，没有 `.deb`

Tier 1 的 Linux 面是 Ubuntu 22.04/24.04、Debian 12/13 和 RHEL/Rocky/AlmaLinux 9/10。
`.deb` 只覆盖其中一半，另一半需要 `.rpm`；而 AppImage 是唯一一种在这六个发行版上都能
直接双击运行的单文件格式。与其做半套包管理支持，不如只出一种全覆盖格式。

### 为什么没有 Windows

- 本项目 Tier 1 支持矩阵**明确排除** Windows、WSL 与 32 位。
- 桌面壳本身只是 UI，真正干活的是 Python `lobster0` Core，而 Core 的安装器同样不支持 Windows；
  出一个 Windows 安装包只会让用户装到一个必然连不上 Core 的壳。
- Windows 代码签名需要另一套证书，未签名的 `.exe` 会触发 SmartScreen 警告。

`desktop/electron-builder.json` 里没有任何 `win`/`nsis` 段，
`tests/test_desktop_packaging.py::test_windows_is_deliberately_not_packaged` 会阻止有人半途加回来。

## 3. 版本一致性

`src/lobster0/_version.py` 的 `__version__` 是全仓唯一版本源。桌面包的产物文件名由
electron-builder 的 `${version}` 模板渲染，而 `${version}` **只**来自 `desktop/package.json`。
因此这里必须绑死，否则 Release 上会出现 `lobster0-desktop-0.1.0-*` 这种与 tag 不符的包，
而其他任何门禁都发现不了（`release-manifest.json` 不收录桌面包）。

三道绑定：

1. `desktop/package.json` 的 `version` 已从 `0.1.0` 改为 `0.7.0`。
2. `tests/test_desktop_packaging.py::DesktopVersionAgreementTest` 断言
   `desktop/package.json["version"] == lobster0.__version__`，离线、随每次全量 unittest 运行。
3. `release.yml` 的 `guard` 作业把 `desktop/package.json` 的版本与 tag、`_version.py`
   绑成同一个事实；`desktop-bundles` 作业开工前再校一次。

## 4. 发布链路接入

新增作业 `desktop-bundles`：

- `needs: [guard, offline-gate, draft-release]`——离线门禁没过就不开构建。
- 矩阵两个条目：`macos-14`（`--mac`）与 `ubuntu-24.04`（`--linux`）。Electron 每个架构都是
  官方预编译产物，本应用又有 `npmRebuild: false`（没有需要重编的原生依赖），所以一个 runner
  就能同时产出该 OS 的 x64 与 arm64 包。
- 构建顺序：固定 Node 24.18.0 → `pnpm --dir tui install/build` → `pnpm --dir desktop install/build`
  → `electron-builder`。**`tui` 必须先 build**：桌面主进程把 `@lobster0/pi-tui` 当外部依赖打进
  asar，而 tui 包没有 `prepare` 脚本，不先编译 `tui/dist` 就会打出一个空的 pi-tui。
- 上传：每个产物计算 `.sha256` sidecar，与产物一起 `gh release upload` 到草稿 Release。

### 桌面包为什么不进 `release-manifest.json`

`release-manifest.json` 是**安装器**的封闭世界事实源，`verify_release_artifacts.py` 会要求
artifact 目录与 manifest 逐文件相等。`.dmg`/`.AppImage` 不是安装器的输入，把它们塞进 manifest
需要同时改 schema、`install/models.py` 的严格解析和一整套 manifest 测试夹具，等于为了打包
去动安装信任根。这里选择不动 manifest，改为让桌面包接受**另外两道既有门禁**：

| 门禁 | 桌面包如何被覆盖 |
| --- | --- |
| `attestation` | 先按 `.sha256` sidecar 复核 6 个产物，再把它们加进 `actions/attest` 的 subject-path |
| `publish` | 转正前重新按 sidecar 复核摘要，并对每个桌面产物执行 `gh attestation verify` |

`attestation` 的 `needs` 增加了 `desktop-bundles`，`publish` 因此传递依赖桌面构建：
**桌面包构建失败会阻断整个 stable 发布**，不会出现「主产物已转正、桌面包缺席或未校验」的状态。
两处都硬断言 `test "${#desktop[@]}" -eq 6`，少一个产物即失败。

被刻意保持不变的事实：`assemble` 不依赖 `desktop-bundles`，manifest/SHA256SUMS/installer 的装配
顺序与内容一字未动；`assemble` 下载时用的 `--pattern '*.sha256'` 只会带进桌面 sidecar，
而它在 `find ... ! -name '*.sha256'` 处被排除，`release-artifacts/` 仍是封闭世界。

## 5. 签名与公证：当前状态是「明确未签名」

**没有任何签名。** 仓库里不存在也不会引入任何证书、Team ID、Apple ID 或签名密钥。

| 平台 | 现状 |
| --- | --- |
| macOS `.dmg` / `.zip` | 未签名、未公证。作业里设 `CSC_IDENTITY_AUTO_DISCOVERY=false`，让「未签名」是明确、可复现的结果，而不是 runner keychain 的偶然状态；`electron-builder.json` 里 `mac.notarize: false`。 |
| Linux `.AppImage` | AppImage 本来就没有强制签名机制，用户侧行为不受影响。 |
| Windows | 不产出。 |

### 用户实际会遇到什么

**macOS**：从浏览器下载的 `.dmg` 会带上 quarantine 属性，Gatekeeper 会直接拒绝，
提示类似「无法打开 "Lobster0"，因为 Apple 无法检查其是否包含恶意软件」。
打开步骤（macOS 13+）：

1. 双击 `.dmg`，把 `Lobster0.app` 拖进「应用程序」。
2. 首次打开时会被拒绝，点「完成」。
3. 打开「系统设置 → 隐私与安全性」，在「安全性」区域找到刚才被拦下的 Lobster0，点「仍要打开」。
4. 再次确认「打开」。之后就不会再提示。

或者在终端里显式移除 quarantine 属性：

```
xattr -d com.apple.quarantine /Applications/Lobster0.app
```

**Linux**：AppImage 没有 Gatekeeper 等价物，下载后 `chmod +x` 即可运行。

### 维护者要怎样才能改成已签名

macOS 签名需要一份 Apple Developer ID Application 证书；公证还需要 Apple ID +
app-specific password（或 App Store Connect API key）与 Team ID。要打开签名：

1. 在仓库 Secrets 里配置 `CSC_LINK`（base64 的 `.p12`）与 `CSC_KEY_PASSWORD`。
2. 在 `desktop-bundles` 作业里把它们注入环境，并移除 `CSC_IDENTITY_AUTO_DISCOVERY=false`。
3. 公证再加 `APPLE_ID` / `APPLE_APP_SPECIFIC_PASSWORD` / `APPLE_TEAM_ID`，并把
   `electron-builder.json` 的 `mac.notarize` 打开、`hardenedRuntime` 设为 `true`。
4. **同时必须修改** `tests/test_install_matrix_contract.py::test_no_workflow_carries_a_long_lived_publishing_token`
   ——它当前断言工作流里除 `GITHUB_TOKEN` 外不出现任何 `secrets.*` 引用。这条测试是故意留的闸：
   引入签名凭据必须是一次被明确评审的动作，不能顺手加进去。

在完成上述步骤之前，产物就是未签名的，文档也如实这么写。

## 6. 运行前提（重要）

打好的桌面包**不自带 Python Core**。主进程通过 `LOBSTER0_PYTHON` 与 `LOBSTER0_HOME`
两个环境变量拉起 `python -m lobster0.bridge`；从 Finder / 桌面环境启动的 GUI 应用拿不到
shell 环境，所以直接双击安装好的应用会在首屏报 `缺少 Python Bridge 启动配置`
（已在本机对真实 `.app` 实测复现）。

当前可用的启动方式仍是仓库根目录的 `start-desktop.command`，它会设置好这两个变量。
让安装包能独立可用需要主进程具备默认发现能力（例如回落到 `~/.local/bin/lobster0`
与 `~/.lobster0`），这是本次打包工作之外的、需要单独走 RED→GREEN 的改动。

| 文件 | 覆盖 |

| `tests/test_desktop_packaging.py`（18 用例） | 配置文件存在且是良构 JSON；依赖全部精确固定；`pnpm-lock.yaml` 与 `package.json` 逐条同步；appId/productName/分类齐备；产物名带 `${version}`/`${arch}`；平台与格式矩阵；无 Windows 目标；`publish: null`；打包内容白名单；输出目录被 gitignore；无任何签名凭据；`notarize: false`；桌面版本等于 `__version__` |
| `tests/test_install_matrix_contract.py::DesktopReleaseArtifactTest`（8 用例） | `desktop-bundles` 作业存在且矩阵正确；只在离线门禁之后运行；`--publish never` 且构建步骤看不到 token；`CSC_IDENTITY_AUTO_DISCOVERY=false`；sidecar 交接；attestation 先复核再签名；publish 转正前重新校验；guard 绑定桌面版本 |

lockfile 一旦落后于 `package.json`，桌面打包会在发布当天才失败。
