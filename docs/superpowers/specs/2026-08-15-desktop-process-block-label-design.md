# 「过程 N 步」的 N 到底数的是什么

> 日期：2026-08-15
> 文档类型：功能设计（**写于实现之前**）
> 状态：`DRAFT FOR REVIEW / IMPLEMENTATION PENDING`
> 相关：[视觉重做 P1](2026-08-14-desktop-visual-production-grade-redesign.md)

## 1. 起因

Owner 展开一个标着「过程 **1 步**」的折叠块，里面是整整一屏的思考：三条现状判断、
五条候选融资案例、三条应对方案。

> 你这个明显不是 1 步过程啊 为什么叫一步 里面那么多步骤

## 2. 现状核查

`task-workbench.tsx` 渲染的是 `block.items.length`，而 `items` 是
`timeline-blocks.ts` 里 `ProcessItem` 的数组。`ProcessItem` 有三种：
`reasoning` / `tool` / `local`。

关键在 `tui/src/state.ts`：**一整轮的思考只产生一个 `reasoning` 条目**——
`event.model_reasoning` 来一次就 `appendItem` 一条，正文再长也是一条。

于是计数把两种完全不同的东西当成同一单位：

| 实际内容 | 现在显示 |
| --- | --- |
| 一屏思考，0 次工具调用 | 过程 1 步 |
| 0 思考，1 次 `read_file` | 过程 1 步 |

**「步」这个词承诺的是可数的动作，而思考不是动作。** 标签因此既不准确，也不能
帮人判断「值不值得展开」——而那正是折叠块唯一要回答的问题。

## 3. 方案：数真正可数的，其余如实描述

折叠块的标题改为描述**里面有什么**：

| 块内容 | 标题 |
| --- | --- |
| 只有思考 | 过程 · 思考 |
| 只有工具 | 过程 · 3 次工具调用 |
| 两者都有 | 过程 · 思考 · 3 次工具调用 |

**只有工具调用被计数。** 它是离散动作：调了三次就是三次，数字有意义。思考是一种
状态而不是若干动作，写成「思考」即可——想知道有多长，展开就看到了。

### 3.1 为什么不改成"数思考里的段落/条目"

试过这个方向，否掉了：模型的思考正文没有稳定结构，有时是编号列表、有时是几段
散文。按换行或编号去数，得到的是**排版的数字**，不是过程的数字——那比现在这个
误导更深，因为它看起来更精确。

### 3.2 `local` 条目

本地提示（如中断说明）不计入标题：它们不是 Agent 做的事，是界面对用户说的话。
展开后仍然显示。

## 4. 不可放宽的边界

- 折叠块的展开/收起行为与 `aria-expanded` 不变（P1 刚修好的矢量箭头也不动）；
- 标题必须能在**不展开**的情况下回答「这里面值不值得看」；
- 不引入需要解析模型正文的逻辑——见 §3.1。

## 5. TDD 起点

- 只有思考时标题含「思考」且**不含数字**（防止回到按条目计数）；
- 只有工具时标题是「N 次工具调用」，N 等于工具条目数；
- 两者都有时两部分都出现；
- `local` 条目不影响标题，但展开后仍渲染；
- 只有 `local` 时标题不为空（空标题无法区分"没有内容"与"坏了"）。

## 6. 退出条件

1. Owner 那种「一屏思考」的块不再显示为「1 步」；
2. 连续三次工具调用显示为「3 次工具调用」；
3. Desktop 全量测试、typecheck、build 通过。

## 7. 明确不做

- 解析思考正文以推断步骤数（§3.1）；
- 改变过程块的分组规则（`groupTimeline` 不动）；
- 在标题里显示耗时或 token——那是 `MessageTelemetry` 的职责，已经在回复下方。
