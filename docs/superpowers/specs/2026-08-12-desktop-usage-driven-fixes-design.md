# 真实使用驱动的六处改动：决策与边界

> 日期：2026-08-12
> 文档类型：补写的设计说明（**实现先于本文档**，见 §1）
> 相关：[D2a 定时任务](2026-08-11-desktop-d2a-automation-control-design.md)、[D3 共享产物](2026-08-11-desktop-d3-artifacts-design.md)

## 1. 为什么这份是补写的

D1～D3 与 Phase 9 都是先写设计再动手。但会话中途由 Owner 实际使用暴露出的问题，
我按「先修再说」处理了，**没有留下设计文档**——它们散在提交信息里。

Owner 直接指出了这一点。其中两处明显不该省：

- **`http_get` 的可信网段豁免**：它放宽了一道安全边界。只留在提交信息里，将来没人
  能快速找到「为什么当初允许了 `198.18.0.0/15`」；
- **自动化运行详情**：改了 Bridge 投影、错误码语义与会话可达性边界，体量与 D2a 的
  一个子项相当，只因为它长自一句抱怨就跳过了文档。

本文档补上这些决策与边界。**它不假装是事前设计**——记录的是已落地代码的判断依据。

## 2. `http_get` 可信网段豁免（安全边界放宽）

### 2.1 起因

Owner 的机器用 fake-IP 模式代理（Surge / Clash 一类），所有域名解析到
`198.18.0.0/15`（RFC 2544 基准测试保留段），真实流量由代理转发。而 `http_get` 的
SSRF 防护判定「非公网即拒绝」，结果是**这台机器上 `http_get` 访问任何外部站点都不通**。

实测：`api.github.com → 198.18.0.56`。

### 2.2 决定

新增 `tools.http_get.trusted_cidrs`，默认为空（行为不变）。Owner 显式声明自己的
网段后才放行。

### 2.3 不可放宽的红线

豁免**不能打开真正危险的地址**，无论调用方写了什么——包括 `0.0.0.0/0`：

| 永远拒绝 | 原因 |
| --- | --- |
| 回环 `127.0.0.0/8`、`::1` | 本机服务 |
| 链路本地 `169.254.0.0/16` | 含 `169.254.169.254` 云元数据端点 |
| RFC1918 `10/8`、`172.16/12`、`192.168/16` | 内网横向移动 |
| 唯一本地 `fc00::/7`、组播、保留段 | 同上 |

实现上不是「先放行再排除」，而是：公网直接放行 → 命中红线直接拒绝 → 剩下的才看
豁免列表。有测试专门断言 `0.0.0.0/0` 打不开回环与云元数据。

### 2.4 为什么不自动识别

自动检测「大量域名都解析到 198.18/15 就放行」看起来更省事，但**自动放宽安全边界**
本身就是危险模式：一旦 DNS 被污染成保留段，防护会自己让路。Owner 显式声明是
一次有意识的授权，成本只有一行配置。

## 3. 自动化运行详情

### 3.1 起因

一次跑了 55 秒、22518 token、写出完整答案的运行，界面上只显示「时间 + 状态 +
`automation_terminal_response_missing`」。Owner 的原话是「看不到任何信息，AI 到底
执行了没有」。

### 3.2 下发什么、不下发什么

| 字段 | 下发 | 理由 |
| --- | --- | --- |
| `result_preview`、用量、起止时间、`turn_id` | ✅ | 它们本来就在库里，只是从没投影出去 |
| 任务的 `prompt` | ✅ | 是 Owner 自己写的内容。D2a 出于「不泄露敏感内容」收敛掉了，现在看尺度收得太紧 |
| `response_json` 完整正文 | ❌ | 界面用 `turn_id` 跳到那次对话看即可，右栏不该被一大段 Markdown 撑爆 |
| `snapshot_json` | ❌ | 含投递目标等界面不需要的内容 |

### 3.3 错误码保留原码

已知错误码翻成中文，**未知码显示成「执行失败（xxx）」而不是笼统一句「失败」**。
笼统化会让 Owner 和维护者都无从排查。

同理，Core 侧的 `AutomationStateError` 此前被压成一个 `automation_state_conflict`，
界面因此分不清「已结束」（重试永远无用）与「版本冲突」（刷新即可）。现在保留具体
原因，但走**白名单**——不把任意异常文本当错误码送出去。

### 3.4 失败的运行也记录产出

此前只有判定成功的分支写 `result_preview` 与 `usage`。改为失败也保留，但**只在模型
确实产出了正文时**：Provider 直接抛错时没有正文可留，不凭空构造（并有测试确认
Provider 的错误正文不会经由 preview 泄漏）。

这不改变成功语义：`terminal_response` 缺席依然判失败，只是失败也留下证据。

### 3.5 打开 automation 渠道的会话

`history` 原本只认 `cli` 渠道，而定时任务的会话在 `automation`——偏偏它最需要回放，
因为没有实时事件流。放开为 `cli` + `automation` 两个**本地**渠道。

**飞书 / Discord 等 IM 渠道仍然打不开**，有测试专门守这条边界：放开 automation
不等于放开私聊。

## 4. 其余四处的判断

### 4.1 权限模式改为带说明的卡片

四个小写单词（safe/smart/autopilot/yolo）说明不了该选哪个。文案对着
`policy/engine.py` 的真实判定写，不是想当然：`SAFE`/`SMART` 走 `_supervised_action`；
`AUTOPILOT`/`YOLO` 对可信 Owner 直接放行；**只有 YOLO 连 HIGH 风险动作也不再询问**。
后两档标「需谨慎」。

### 4.2 定时任务默认「立即执行一次」

临时任务多数就是想现在跑一下。实现上「立即」= 界面按当下时刻生成一条 `once` 调度。

**Core 侧必须同时改**：`automation.create` 原本把 `misfire_grace_seconds` 硬编码成 0，
于是界面生成的「现在」在请求送达 Core 时已是过去，必然被判 `schedule_misfire`。改用
配置值（默认 300 秒）容忍这段传输耗时。

### 4.3 已完成的任务不再显示「取消」

单次任务跑完即 `completed`，Core 会以 `task_terminal` 拒绝任何写操作。界面的终结
判定原本只认 `cancelled`，于是给已完成的任务留着「取消」按钮——点了必然失败，还提示
「请稍后重试」，而这个状态重试一万次也一样。

### 4.4 错误码如何跨过 IPC

Electron 序列化 `Error` 时只保留 `message`，自定义的 `code` 属性会丢。所以在
`ipcMain.handle` 那一层把码写进 message，渲染进程再解析。

**Web 传输不走这条**——那条路径本来就单独传 `code` 字段。最初把包装加在共用的
`registerDesktopIpc` 上，正好被 Web 传输的测试挡下来了。

## 5. 这批改动共同暴露的问题

八处「设计文档承诺了、代码也写了，但功能实际不通」，详见
[分 Phase 落地文档 §4.11](../../engineering/desktop/20260810_桌面多Agent分Phase落地.md)。

**没有一处是逻辑写错**——问题全在部件之间的接缝。单元测试验证的是「组件在被正确
调用时行为正确」，而不是「组件真的被调用了」。
