# README 与产品截图更新设计

## 目标

把中文 README 从面向项目内部的技术说明，改成第一次访问者也能快速看懂的产品首页：先说明
Lobster0 能替用户做什么，再给出安装、安全和技术证据。整体篇幅相对当前版本缩短约 30%，
但不删除关键技术事实，也不把未完成的 Live Gate 或发布工作写成已经完成。

## 读者与叙事

主要读者是第一次看到 Lobster0、正在判断它是否值得安装的人。README 按以下顺序组织：

1. 一句话价值与 Desktop 主图；
2. 三到四个真实、常见的使用场景；
3. 当前能做什么，以及它为什么可控；
4. 最短可行的安装和启动方法；
5. 压缩后的架构、验证状态与深度文档入口。

文案使用短句和常用词。首次出现的 `Policy`、`Tool`、`Approval` 等术语随即用中文解释，
避免用 Phase 编号、内部组件名或测试计数承担产品介绍。

## 截图方案

最终保留 2～5 张图，默认制作以下 4 张；若某张不能从最新真实界面得到干净、可信的画面，
宁可减少数量，也不使用旧界面或伪造 Live 结论。

| 位置 | 界面 | 代表性任务 | 主要信息 |
| --- | --- | --- | --- |
| README 首屏 | Desktop | 读取工作区会议材料，整理周报、风险和下周待办 | 普通用户可以直接交付完整工作 |
| 产品预览 | 飞书 | 在聊天中请求同类办公任务并接收 `Claw Trail` 与最终结果 | 离开电脑也能从常用 IM 使用同一个 Agent |
| 产品预览 | TUI | 检查仓库状态、运行测试并总结失败原因 | 开发者可以看到工具过程和运行数据 |
| 产品预览 | Desktop 或飞书 | 本地写入或命令执行前请求审批 | Agent 会行动，但关键动作仍由用户决定 |

所有截图使用隔离的 `LOBSTER0_HOME`、演示 Workspace 和无敏感信息的固定内容。画面只保留目标应用
窗口；不出现真实姓名、头像、私人聊天、Token、路径中的个人信息、调试窗口或无关通知。截图正文不写
“介绍 Lobster0 能力”这类自我宣传提示，而使用真实工作目标和可检查的产物。

截图必须来自当前仓库构建。允许使用本地固定 Provider 生成可重复的演示响应，但 README 要明确说明
其证据边界；飞书若不是实际平台画面，不得标成 Live 截图。

## README 内容取舍

以当前中文 README 的 490 行、28,684 字节为基线，目标约为 330～360 行、20～21 KiB。
保留以下内容：

- 产品定位、主要入口和核心能力；
- 一行安装的真实发布状态与源码安装方法；
- Permission Mode、安全边界和同一 Core 的基本架构；
- 当前验证状态、主要验证命令、路线图和文档入口。

压缩或下沉以下内容：

- 受管 Node 版本、安装器参数和升级失败细节；
- W0/W1、D1～D5 等内部阶段叙述；
- Memory、Automation、Browser 的实现清单和历史测试基线；
- 可由现有产品、架构、运维和评测文档承载的长篇证据说明。

README 只引用已经实现并验证的行为。技术信息继续可查，但不在首页重复完整工程文档。

## 修改范围

- 修改 `README.md`；英文 README 不在本轮范围内。
- 在 `docs/assets/` 新增或替换本轮确认使用的截图。
- 不修改产品代码来迎合截图；若界面本身存在缺陷，单独记录，不混入本轮 README 变更。

## 验收

1. README 首屏在一句话和一张图内讲清产品价值。
2. 2～5 张截图全部来自最新界面，内容干净且用例不重复堆砌。
3. README 相对基线缩短约 30%，关键技术事实和证据状态仍准确。
4. 图片链接有效，`uv run python scripts/validate_docs.py` 与 `git diff --check` 通过。
5. 最终逐张检查原图的裁切、清晰度、隐私信息和文案一致性。
