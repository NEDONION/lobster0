# 实机部署踩坑实录（腾讯云轻量 · Ubuntu 24.04）

> 本文记录一次**真实的**服务器部署全过程：机器选型、每一步命令、以及实际撞到的每一个问题。
> 与 [Linux 服务器部署指南](20260811_Linux服务器部署指南.md) 的分工：那份是**验证过的正确步骤**，本文是**踩坑现场**——为什么会踩、怎么判断、怎么绕过。
>
> **状态：持续更新中。** 部署仍在进行，后续问题会继续追加。

## 环境

| 项 | 值 |
| --- | --- |
| 云厂商 | 腾讯云 轻量应用服务器 |
| 地域 | 北京 |
| 配置 | 4 核 8G / 60GB SSD / 5M 带宽 |
| 镜像 | `Ubuntu24.04-Docker29 29.6.1` |
| 登录用户 | `ubuntu`（非 root，需 sudo） |

### 为什么选这个镜像

候选里还有 Windows Server、Node.js 22.12.0、Debian13、OpenCloudOS、CentOS 等。选 `Ubuntu24.04-Docker29` 的理由：

1. **Ubuntu 24.04 是被验证过的系统** —— 部署指南里那套 28 项全绿的实测就跑在这个版本上；
2. **预装 Docker 有用** —— 沙箱功能需要它，省去自己配置。

明确不能选的：

- **Windows Server** —— Lobster0 完全不支持 Windows，安装器会直接拒绝，Python Core 也没做适配；
- **Node.js 22.12.0 镜像** —— 预装的 Node 是 22.12.0，**低于项目要求的 22.22.3**，反而碍事。

> 关于"不要选应用镜像"的补充：这条建议针对的是宝塔面板那类会改系统配置的镜像。
> `Ubuntu+Docker` 只是纯净系统加一个 Docker，不属于此列。

### 防火墙

**只放行 SSH 22 端口即可。**

飞书渠道走 **WebSocket 长连接**：程序主动连出去，不接受入站回调。因此不需要公网回调地址、域名、证书或内网穿透。轻量服务器默认可能开了 80/443，建议关掉。

## 坑 1：`sudo corepack` 找不到命令

### 现象

装完 Node 后，命令链最后一步失败：

```console
$ curl -fsSL -o /tmp/node.tar.xz https://nodejs.org/dist/v24.18.0/node-v24.18.0-linux-x64.tar.xz \
  && sudo mkdir -p /opt/node && sudo tar -xJf /tmp/node.tar.xz -C /opt/node --strip-components=1 \
  && echo 'export PATH=/opt/node/bin:$PATH' >> ~/.bashrc && export PATH=/opt/node/bin:$PATH \
  && sudo corepack enable && node --version
sudo: corepack: command not found
```

### 原因

`sudo` 出于安全考虑会**重置 PATH**（`sudoers` 的 `secure_path`），不会继承你刚 `export` 的 `/opt/node/bin`。

### 第一次尝试（也失败了）

改用完整路径调用：

```console
$ sudo /opt/node/bin/corepack enable && node --version && corepack --version
/usr/bin/env: ‘node’: No such file or directory
```

失败原因是同一个问题的连锁反应：`corepack` 本身是个 Node 脚本，首行是 `#!/usr/bin/env node`。在 `sudo` 的受限 PATH 下，连 `node` 都找不到。

### 正确解法

把 node 系列命令软链到 `/usr/local/bin`——这个目录在 sudo 的默认 `secure_path` 里：

```bash
sudo ln -sf /opt/node/bin/node /usr/local/bin/node
sudo ln -sf /opt/node/bin/npm /usr/local/bin/npm
sudo ln -sf /opt/node/bin/npx /usr/local/bin/npx
sudo ln -sf /opt/node/bin/corepack /usr/local/bin/corepack
sudo corepack enable
```

验证：

```console
$ node --version
v24.18.0
$ corepack --version
0.35.0
```

一次性解决，之后不管是普通用户还是 sudo 调用都能找到 node。

### 为什么容器验证没发现

部署指南的验证是在 Docker 容器里以 **root 直接执行**的，没有经过 `sudo`，因此 PATH 从未被重置。**这类问题只有在真实机器上、以非 root 用户配合 sudo 操作时才会暴露。**

## 坑 2：国内网络访问 GitHub —— 这是整个部署最大的障碍

这一节是国内部署的**核心问题**。不解决它，后面每一步都会卡。

### 现象一：clone 长时间无响应

```console
$ git clone https://github.com/NEDONION/lobster0.git ~/lobster0
Cloning into '/home/ubuntu/lobster0'...
（长时间停在这里）
```

### 现象二：TLS 连接被中断

```console
$ git clone https://github.com/NEDONION/lobster0.git ~/lobster0
Cloning into '/home/ubuntu/lobster0'...
fatal: unable to access 'https://github.com/NEDONION/lobster0.git/':
GnuTLS recv error (-110): The TLS connection was non-properly terminated.
```

这个报错**不是**仓库、权限或证书问题，是连接在传输中途被切断。本仓库 `.git` 完整历史约 72MB，链路不稳时很难一次拉完。

### 解法（按成功率排序，逐个试）

**① 浅克隆 + 放宽超时**

```bash
git config --global http.postBuffer 524288000
git config --global http.lowSpeedLimit 0
git config --global http.lowSpeedTime 999999
rm -rf ~/lobster0 && git clone --depth 1 https://github.com/NEDONION/lobster0.git ~/lobster0
```

`--depth 1` 只取最近一次提交，体积从 72MB 降到几 MB。部署运行完全够用，只有要查历史或切分支才需要完整克隆。

**② 走 GitHub 加速镜像（实测可用）**

```bash
rm -rf ~/lobster0
git clone --depth 1 https://gh-proxy.com/https://github.com/NEDONION/lobster0.git ~/lobster0
```

这次实机部署中，前面几种方式都失败，**这一条成功了**：

```console
Cloning into '/home/ubuntu/lobster0'...
remote: Enumerating objects: 869, done.
remote: Counting objects: 100% (869/869), done.
remote: Compressing objects: 100% (843/843), done.
Receiving objects:  14% (128/869), 1.41 MiB | 127.00 KiB/s
```

速度仍然只有 ~127 KB/s，但能稳定完成。

> 镜像站是第三方服务，只用于拉取公开代码。**不要用它推送**，也不要在上面放任何凭据。
> 各镜像站可用性随时间波动，某个不通就换下一个（如 `ghfast.top`、`hub.gitmirror.com`）。

**③ 绕开 git，直接下载压缩包**

```bash
curl -fL -o /tmp/l.tar.gz https://github.com/NEDONION/lobster0/archive/refs/heads/main.tar.gz
mkdir -p ~/lobster0 && tar -xzf /tmp/l.tar.gz -C ~/lobster0 --strip-components=1
```

走普通 HTTPS 下载，比 git 协议更容易穿过不稳定链路。缺点是没有 git 历史，无法 `git pull` 更新。

## 坑 3：不止 git 要换源 —— 后续步骤同样卡在国外源

只解决 clone 是不够的。后面还有三处要从境外拉大文件：

| 步骤 | 默认源 | 拉什么 |
| --- | --- | --- |
| `uv sync` | python-build-standalone（GitHub） | Python 3.12 解释器本体 |
| `uv sync` | PyPI | 全部 Python 依赖 |
| `pnpm install` | npm registry | 前端依赖 |

**在 clone 完成后、`uv sync` 之前一次性配好**，可以省掉后面反复踩坑：

```bash
cat >> ~/.bashrc <<'EOF'

# 国内源加速
export UV_DEFAULT_INDEX=https://pypi.tuna.tsinghua.edu.cn/simple
export UV_PYTHON_INSTALL_MIRROR=https://gh-proxy.com/https://github.com/astral-sh/python-build-standalone/releases/download
EOF
source ~/.bashrc

npm config set registry https://registry.npmmirror.com
```

验证：

```console
$ echo $UV_DEFAULT_INDEX
https://pypi.tuna.tsinghua.edu.cn/simple
$ npm config get registry
https://registry.npmmirror.com
```

两个 uv 变量名的依据：`uv python install --help` 中标注 `[env: UV_PYTHON_INSTALL_MIRROR=]`，
`uv pip install --help` 中标注 `[env: UV_DEFAULT_INDEX=]`。不要用已废弃的 `UV_INDEX_URL`。

## 已知问题速查

| 现象 | 原因 | 解法 |
| --- | --- | --- |
| `sudo: corepack: command not found` | sudo 重置 PATH | 软链 node 系列到 `/usr/local/bin` |
| `/usr/bin/env: ‘node’: No such file` | corepack 是 Node 脚本，sudo 下找不到 node | 同上 |
| `git clone` 长时间无响应 | 国内访问 GitHub 慢，仓库 72MB | `--depth 1` 浅克隆 |
| `GnuTLS recv error (-110)` | 连接被中途切断 | 走 `gh-proxy.com` 镜像（实测可用） |
| `uv sync` 卡在下载 Python 或依赖 | 默认走 GitHub 与 PyPI | 配 `UV_PYTHON_INSTALL_MIRROR` 与 `UV_DEFAULT_INDEX` |
| `pnpm install` 极慢 | 默认走 npm 官方 registry | `npm config set registry https://registry.npmmirror.com` |
| `heartbeat.timezone must be a valid IANA timezone` | uv 的 Python 不带时区数据库 | 已修复（补 `tzdata` 依赖），拉最新代码即可 |
| `This project is configured to use 10.14.0 of pnpm` | Node 24 的 corepack 拉起 pnpm 11 | 先 `corepack prepare pnpm@10.14.0 --activate` |

## 给国内部署者的一句话总结

**先换源，再动手。** 本文的坑 2 和坑 3 合计占了这次部署绝大部分的时间。
把 GitHub 镜像、PyPI 源、Python 解释器源、npm 源四处一次配好，
后面的步骤基本就是照着[部署指南](20260811_Linux服务器部署指南.md)顺序执行。
